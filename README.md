# Sentry

Sentry ловит вебхуки о новых задачах из Яндекс Трекера и пишет в чат Яндекс
Мессенджера, когда за короткое окно (по умолчанию 30 минут) приходит несколько задач
**с одной категорией и одним тегом** — признак массовой проблемы.

Обращения заводит клиентская поддержка: оператор заполняет форму (сайт или
мобильное приложение), из неё создаётся задача в Трекере, дальше её разбирает
техническая поддержка. Sentry сигналит техподдержке о всплеске раньше, чем он
станет виден в очереди.

> Имя внутреннее и не связано с продуктом sentry.io. В Docker образ имеет
> локальный тег `sentry-fl`, чтобы не путать с публичным образом.

Теги `Сайт` и `МП` разделяют два канала обращений (сайт / мобильное приложение),
у которых пересекаются категории.

## Мультиочередь

Сервис обслуживает несколько **очередей** одновременно. У каждой очереди свои:

- чат Яндекс Мессенджера (`chat_id`, при необходимости — отдельный токен бота);
- окно поиска дублей, порог срабатывания и кулдаун уведомлений;
- список каналов (тегов);
- URL вебхука `/webhook/<ключ>` и, опционально, отдельный токен.

Дедупликация и аналитика считаются **в пределах очереди**. Всё редактируется в
админке без перезапуска. Старый эндпоинт `POST /webhook` (без пути) продолжает
работать и направляется в очередь по умолчанию (`DEFAULT_QUEUE_KEY`).

### Кулдаун уведомлений

При массовой проблеме порог пробивает не одна задача, а десятки — без кулдауна
на каждую из них уходит отдельное сообщение в чат. `alert_cooldown_minutes` у
очереди (или общее `ALERT_COOLDOWN_MINUTES`) ограничивает: **один алерт на
`категория+тег` за N минут**. Промежуточные дубли всё равно попадают в журнал
(`notified: false`) и в аналитику — молчит только чат. `0` — старое поведение
(сообщение на каждую задачу всплеска).

## Быстрый старт (Docker)

Нужен только **Docker** с плагином **compose**.

```bash
cd sentry
cp .env.example .env

# заполнить в .env:
#   ADMIN_PASSWORD          — пароль для входа в /admin
#   YANDEX_MESSENGER_TOKEN, YANDEX_MESSENGER_CHAT_ID
#   WEBHOOK_TOKEN (рекомендуется) — python -c "import secrets; print(secrets.token_urlsafe(32))"

docker compose up -d --build
```

Проверка:

```bash
curl http://localhost:8000/health
# {"status":"healthy","storage":"sqlite","queues":1,...}
```

- Админка: `http://<host>:8000/admin`
- Дашборд: `http://<host>:8000/dashboard`
- Swagger UI: `http://<host>:8000/docs`

С `make`: `make up`, `make logs`, `make down`, `make token`.

## Админка (`/admin`)

Вход по одному паролю (`ADMIN_PASSWORD`). Сессия — cookie на 7 дней. Три вкладки:

- **Очереди** — список очередей карточками. Для каждой: статус, окно, порог,
  каналы, готовый URL вебхука и токен (кнопка «копировать»), счётчики
  (задач в окне, событий, когда было последнее). Кнопки: *Редактировать*,
  *Тест уведомления* (шлёт тестовое сообщение в чат очереди), *Очистить данные*,
  *Удалить*. Кнопка **+ Добавить очередь** — форма с ключом, названием, `chat_id`,
  окном, порогом, каналами.
- **Общие настройки** — значения по умолчанию и глобальные параметры: URL и токен
  Мессенджера, URL Трекера, часовой пояс, срок хранения аналитики, размер журналов,
  общий токен вебхука, очередь по умолчанию, уровень логирования, пароль админки.
  Секреты показываются как «задано / не задано», меняются вводом нового значения.
- **Логи** — хвост файла лога процесса, выбор числа строк, обновление.

Приоритет значений: **БД (админка) → переменная окружения → значение по умолчанию.**
`.env` задаёт стартовые значения; после первого запуска правки идут через админку.

Если `ADMIN_PASSWORD` пуст — вход в админку отключён (в лог пишется предупреждение).

## Настройка триггера в Яндекс Трекере

Один триггер на создание задачи → действие **«Вызвать HTTP»**:

- **Метод:** `POST`
- **URL:** `http://<host>:8000/webhook/<ключ-очереди>`
  (или `http://<host>:8000/webhook` для очереди по умолчанию)
- **Заголовки:** `Content-Type: application/json`
  и, если задан токен, `X-Webhook-Token: <токен очереди или общий>`
- **Тело:**

```json
{
  "issue_key": "{{issue.key}}",
  "summary": "{{issue.summary}}",
  "category": "{{issue.category}}",
  "tag": "{{issue.tags}}"
}
```

`category` и `tag` подставляются из реальных полей задачи (категория и «Теги»,
где стоит `Сайт` или `МП`). Можно также указать очередь прямо в теле — поле
`"queue": "<ключ>"` (путь в URL важнее). Прочие поля тела сервис игнорирует.

## Логирование

- **Файл:** `data/sentry.log` (в Docker `/app/data/sentry.log`, тот же том, что и БД —
  переживает перезапуск, попадает в бэкап). Ротация: `LOG_MAX_BYTES` × `LOG_BACKUP_COUNT`
  (по умолчанию 5 МБ × 5).
- **Консоль (stdout):** то же самое, забирается Docker (`docker compose logs -f`,
  ротация 3 × 10 МБ в `docker-compose.yml`).
- **Через API/админку:**
  - `/admin` → вкладка «Логи»;
  - `GET /api/v1/logs?lines=200` (под токеном) — хвост файла лога;
  - `GET /api/v1/log?limit=50&queue=<ключ>` (под токеном) — прикладные журналы
    входящих и сработавших алертов из БД.
- **Уровень:** `LOG_LEVEL` (или вкладка «Общие настройки»), меняется на лету.

Скопировать файл лога из контейнера:
`docker compose cp sentry:/app/data/sentry.log ./sentry.log`

## Обновление

```bash
git pull
docker compose up -d --build
```

Схема БД мигрирует автоматически (в таблицы добавляется `queue_key`, старые данные
приписываются к очереди по умолчанию). Том с базой сохраняется. Полный сброс:
`docker compose down -v` либо `POST /api/v1/clear` (весь сервис) /
`POST /api/v1/clear?queue=<ключ>` (одна очередь).

## Переменные окружения

| Переменная | По умолч. | Назначение |
|---|---|---|
| `ADMIN_PASSWORD` | пусто | пароль входа в `/admin`; пусто — админка отключена |
| `YANDEX_MESSENGER_URL` | `https://ymnb.av.ru/api/messages/send` | эндпоинт отправки сообщений |
| `YANDEX_MESSENGER_TOKEN` | — | OAuth-токен бота (общий для очередей) |
| `YANDEX_MESSENGER_CHAT_ID` | — | чат очереди по умолчанию (`0/0/<uuid>`) |
| `WEBHOOK_TOKEN` | пусто | общий токен; если задан — `/webhook*` и служебные ручки требуют `X-Webhook-Token` |
| `TRACKER_URL` | `https://tracker.yandex.ru` | база для ссылок на задачи |
| `DEFAULT_QUEUE_KEY` | `default` | ключ очереди для legacy `POST /webhook` |
| `WINDOW_MINUTES` | `30` | стартовое окно очереди по умолчанию |
| `ALERT_THRESHOLD` | `1` | стартовый порог (совпадений в окне до алерта) |
| `ALERT_COOLDOWN_MINUTES` | `0` | не повторять алерт по `категория+тег` чаще раза в N мин (`0` — выкл) |
| `DB_PATH` | `data/sentry.db` | путь к файлу SQLite (в Docker — `/app/data/...`) |
| `EVENTS_RETENTION_DAYS` | `365` | сколько дней хранить события аналитики (`0` — не чистить) |
| `MAX_LOG_ENTRIES` | `200` | сколько последних записей хранить в каждом журнале БД |
| `TIMEZONE_OFFSET` | `3` | сдвиг TZ для вывода времени |
| `LOG_LEVEL` | `INFO` | уровень логирования |
| `LOG_DIR` / `LOG_FILE` | каталог БД / `sentry.log` | путь файла лога |
| `LOG_MAX_BYTES` / `LOG_BACKUP_COUNT` | `5242880` / `5` | ротация файла лога |
| `PORT` | `8000` | порт на хосте |

После первого старта эти значения (кроме `ADMIN_PASSWORD`, `DB_PATH`, `PORT`, `LOG_*`)
переопределяются из админки.

## Эндпоинты

| Метод | Путь | Защита |
|---|---|---|
| `POST` | `/webhook` | токен (очереди по умолчанию или общий) |
| `POST` | `/webhook/{queue_key}` | токен очереди или общий |
| `POST` | `/webhook[/{queue_key}]?dry_run=1` | то же; ничего не пишет и не шлёт — показывает, что *произошло бы* (проверка полей триггера) |
| `GET` | `/health` | нет |
| `GET` | `/api/v1/queues` | нет (только ключ + название) |
| `GET` | `/api/v1/stats` | нет |
| `GET` | `/api/v1/window?queue=` | `WEBHOOK_TOKEN` — что сейчас в окне дедупа (категории/теги, счётчики, `issue_key`) |
| `GET` | `/api/v1/log?limit=50&queue=` | `WEBHOOK_TOKEN` |
| `GET` | `/api/v1/logs?lines=200` | `WEBHOOK_TOKEN` |
| `POST` | `/api/v1/clear?queue=` | `WEBHOOK_TOKEN` |
| `POST` | `/api/v1/test-notify?queue=` | `WEBHOOK_TOKEN` |
| `GET` | `/dashboard` | нет |
| `GET` | `/api/v1/analytics/overview?days=30&queue=` | нет |
| `GET` | `/api/v1/analytics/events?days=30&queue=` | `WEBHOOK_TOKEN` |
| `GET` | `/admin` , `/admin/api/*` | пароль (cookie-сессия) |
| `GET` | `/` , `/docs` | нет |

## Дашборд

`GET /dashboard` — самодостаточная HTML-страница (графики инлайн, без CDN).
Селектор очереди в шапке (или «Все очереди»). Показывает KPI-сводку, поток задач
по времени, топ категорий, каналы, всплески, тепловую карту час×день недели и
список последних всплесков. Диапазон 7 / 30 / 90 / 365 дней, автообновление.

Данные — из append-only таблицы `events` (одна строка на обработанную задачу),
хранятся `EVENTS_RETENTION_DAYS` дней. Для внешнего BI: `GET /api/v1/analytics/overview`
и `GET /api/v1/analytics/events` (с фильтром `queue=`).

`/dashboard` и `/api/v1/analytics/overview` открыты — если хост доступен извне,
закройте на сетевом уровне.

## Эксплуатация

- **Один процесс.** Состояние в SQLite-файле, доступ через одно соединение под
  замком — несколько воркеров/реплик нельзя. `docker-compose.yml` — один контейнер.
- **Бэкап.** `docker compose cp sentry:/app/data/sentry.db ./backup.db`
  (там же лежит `sentry.log`).
- **Содержимое БД:** `docker compose exec sentry python db_inspect.py`
  (печатает `settings`, `queues` и рабочие таблицы).
- **Логи** контейнера: `docker compose logs -f`; файл: `/app/data/sentry.log`
  или вкладка «Логи» в админке.
- **Автозапуск** после перезагрузки: `restart: unless-stopped`.
- **Доступ извне.** Задайте `WEBHOOK_TOKEN`, закройте порт файрволом (оставив
  Трекер), а для локального доступа поменяйте проброс порта в compose на
  `"127.0.0.1:${PORT:-8000}:8000"`. Админку в интернет не выставлять.

## Тесты

```bash
pip install -r requirements-dev.txt
pytest
```

`pytest` изолирован: БД и файл лога уводятся во временный каталог, сеть и
Мессенджер отключены. Покрыто: `ConfigStore` (приоритеты, очереди, миграция),
`SQLiteStorage` (дедуп по категория+тег, окно, обрезка журналов, кулдаун,
аналитика), `DuplicateChecker` (порог, пропуск повторов, подавление кулдауном,
dry-run), HTTP-слой (вебхук, токены, `/api/v1/window`, dry-run, админка),
`YandexMessenger` (сборка запроса, обработка ошибок) и `logging_setup`.
